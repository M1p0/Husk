## 1. 交付目标与边界

- APK 对应真正注册的 iOS App，具有稳定应用标识、独立入口、容器与进程生命周期。
- 启动器在新进程启动时加载一个确定的完整 Husk Runtime 版本。
- App 的业务、Java 状态、原生代码和主要图形执行均在自己的应用边界内。
- A 的普通用户态崩溃只终止 A；共享服务的失败不触发其他 App 的退出。
- A 的资源使用受可执行的限额约束；预算不足时限制 A 或拒绝新任务。
- 每 App 的资源边界包括主进程、所属辅助进程和可归属的共享服务资源。
- 所有 App 仍共享物理内存、内核和驱动；不承诺任意整机压力下 B 永不被系统终止。
- “强内存隔离”仅能描述明确设备、工作负载与预算范围内经过验证的限额行为。
- 图标独立、PID 不同、一次演示成功，均不足以证明完整交付。

以下约束在全部阶段有效：

1. 保留当前手动 JIT 设置；不自动估算、学习、增减 JIT 配额。
2. 保留 Java 工作线程的 32 MiB 原生栈设置；不通过缩小栈掩盖预算不足。
3. 预算不满足时明确拒绝新启动或新辅助任务，不暗中修改上述设置。
4. APK 进程不使用 root；不以全局取消沙箱、关闭 Jetsam 作为设计基础。
5. 管理服务不执行 APK 业务或插件代码，受限的安装服务只处理必要特权操作。
6. 所有 IPC 验证调用身份、应用归属和授权；请求、队列、并发与响应都有上限。
7. 新能力未经设备证据验证前标为“未知”，不可根据越狱名称推定支持。
8. 按用户要求关闭托管 CI/CD，构建与验证在本地手动执行；后续同步上游时不恢复 GitHub Actions workflow，也不重新启用仓库 Actions，除非用户另行要求。现有手动构建脚本保留。

## 2. 当前基线与阶段依赖

当前源码中的落点：

| 项目 | 当前证据 | 后续影响 |
| --- | --- | --- |
| 运行时构建 | `src/app/project.yml` 把翻译层直接编入 application target | 需新增完整 Runtime 构建产物 |
| 资源定位 | `TLUnityView.swift` 使用 `Bundle.main` 查 Java、ANGLE 和系统资源 | 改为明确传入版本根路径 |
| 进程身份 | `android/os/Process.java` 的 PID、UID 仍为固定值 | 需应用内身份映射与访问校验 |
| 信号发送 | `husk-tl-bionic-cxx.c` 对部分正 PID 调用宿主 `kill` | 必须收紧跨应用信号能力 |
| Binder 与 Service | Java Binder 本地调用，Services 在当前进程实例化 | 不代表已支持 Android 多进程 |
| 通知 | `NotificationManager.notify` 记录日志 | 需实现系统通知与身份路由 |
| JIT | `JITBootstrap.swift` 含当前进程的单独授权和分配过程 | 每个新进程需验证对应能力 |

路线调整为两条有共同核心的验证链：**先完成 macOS M0–M5；目标 iOS 27 越狱环境具备后，执行 P0，再接入/复验 P1–P6 的设备部分。** 不等待 iOS P0 才开始核心开发，也不把 Mac 证据转换成 iOS 通过记录。

| Mac 阶段 | 产物与验收 | 对应后续阶段 |
|---|---|---|
| M0 基线 | 在 arm64 Mac 上构建现有 native-runtime harness，验证 Java 启动/重开及 I/O 清理；记录版本和测试日志 | 现状证据，非独立架构交付 |
| M1 Runtime 拆分 | macOS 专用 Runtime 包、稳定 C ABI、显式宿主上下文、版本持有与能力接口；轻量探针加载两个版本 | 复用 P1 的核心设计，设备另行构建 |
| M2 独立外壳 | 两个 Mac `.app`、各自入口/进程/数据、按应用认证的管理 IPC；小型已兼容 APK 分别运行 | P2 的身份/安装核心；iOS 注册与沙箱实现仍待接入 |
| M3 调度与故障 | 在有限工作集下验证并发准入、启动峰值归还、失败释放屏障、服务失联、A 崩溃时 B 连续工作 | P3 策略核心；模拟限额不算系统硬限制 |
| M4 更新与回收 | 使用真实 Mac 进程和锁协议验证不可变 Runtime/APK、执行代次、强杀、更新中断、并发 GC | P4 核心逻辑；iOS 锁与文件访问条件重新验证 |
| M5 集成与移植包 | Mac 桌面/窗口和必要文件/音频桥接、回归用例、平台差异清单；可选 UIKit Simulator 外壳测试 | P5 的已适配部分及 P6 的共用场景 |

M1 提前实现最小不可变目录和防删除持有协议；M2/M3 使用固定版本，不启用自动清理及活动版本自动切换，直到 M4 通过。M2 先完成外壳与身份，完整资源故障验收在 M3 进行。Mac 受控原型可运行有限 APK 工作集，资源控制未强制执行的部分必须明确标记，禁止将其对外描述为受保护的任意并发模式。

P1 同样提前具备最小版本持有协议；P4 再完成设备侧自动发布、并发 GC 与恢复。iOS P1/P2 的阶段性验证只允许受控轻量探针；P3 的真实 APK 压力试验在有效限额下使用固定版本，自动清理和切换保持关闭直到 P4 通过。

复用单位是源码模块、启动 ABI、事务/预算状态机及测试场景。为 macOS、iOS device 和可选 Simulator 分别编译运行库和图形依赖；不得复用错误平台的 Mach-O、签名、JIT 许可或缓存。UIKit/Scene、安装服务、沙箱权限、JIT、后台与资源强制执行通过平台接口接入。

每个宿主输出自己的能力矩阵：`unsupported`、`observed`、`simulated` 或 `enforced-and-verified`。预算模拟器可测试拒绝/失败状态机，但不能把结果写成 macOS 或 iOS 内核已经执行硬限制。未验证限额时使用有限工作集、定点分配失败及受控崩溃注入，不做整机 OOM 试验。

P0 未过关只阻塞依赖该能力的 iOS 阶段，Mac 核心工作继续。iOS P2/P3/P4 的隔离和恢复通过后再进行完整设备集成；iOS 正式交付需要 P5 已声明能力与 P6 真机验收。
每阶段留存通过、失败、未测项；后续成功不能覆盖早期未验证的关键条件。

## 3. P0：目标设备能力探针

**前置条件**：目标 iOS 设备及可用越狱环境具备，选定系统 build 与 bootstrap/签名环境。P0 是设备接入门槛，不是 M0–M5 的前置条件。
每次系统、越狱、签名方式变化，都重新判断相关结论是否失效。

产物：两个最小原生测试 App、独立能力探针、设备能力报告和原始日志。
探针是后续需要编写的产物；本仓库当前没有可直接运行的该组探针命令。

需要验证：

| 探针 | 必须获取的证据 | 不通过时的处理 |
| --- | --- | --- |
| 系统注册 | 两个独立 bundle ID、安装记录、容器、真实 PID、启动归属及 coalition 信息 | 停止原生独立 App 交付 |
| 最小权限 | 非 root 身份；A 不能写 B 容器、发信号或取得 B 的 task port | 停止隔离交付 |
| 公共库装载 | 沙箱内只读/执行指定版本库；不能修改库、索引或其他版本 | 评估保持隔离的受控映射方案；仍不通则停止该装载路线 |
| 独立静默 JIT | 每个新进程单独获准执行生成代码，无需反复切换外部 App | 标记原生启动体验不满足，不推定未来可用 |
| 活跃/非活跃硬限制 | 系统侧限额已生效，状态切换后的限额和超限行为可重复观察 | 不宣称强内存隔离 |
| 辅助资源归属 | WebKit、GPU、解码、JIT helper 等资源能归属和约束到对应 App | 无法核算的类别不进入强隔离支持范围 |
| 锁屏与后台 | 用户授权的后台模式在锁屏、前后台切换后仍按策略执行 | 降级为系统允许的后台能力 |
| 用户强退 | 区分用户停止与可恢复退出，取消排队任务并拒绝旧代次重启 | 禁用自动复活，只保留显式打开 |
| 版本权限 | 两个 App 可分别使用旧、新签名版本，彼此不能修改运行文件 | 停止动态共享版本交付 |

硬限制探针不得只读取一个 entitlement 或 `os_proc_available_memory()` 数值。
应记录限额设置入口、授权要求、有效值、进程状态以及真实超限终止原因。
测试分配必须触及页面；仅保留虚拟地址空间不能证明物理 footprint 限制。
记录干净代码页、私有脏页、JIT 双映射、GPU 资源和系统辅助服务的计费差异。
默认不得假设有 Android cgroup 或可直接使用的 iOS 应用组硬限额机制。
如果只有单进程硬限制，需验证辅助进程配额之和能被约束；否则标为缺口。
强杀资源控制服务后再次触发 A 越限分配，验证硬限制无需该服务存活；同时确认新准入与扩额被拒绝。
不通过的能力保留原始失败信息，不以轮询补丁或提高全局优先级替代结论。

**验收**：每个关键探针有目标设备原始证据和独立复测记录。
**停止条件**：沙箱、独立装载或 JIT 能力不可用时暂停依赖该能力的实机阶段。
若只有资源约束不成立，可继续普通独立进程原型，但必须标明内存隔离降级。

## 4. P1：稳定启动器与完整 Runtime 包

**前置条件**：Mac 核心对应 M1，可先实施；iOS 部分需 P0 证明核心装载路线可行。

产物：轻量启动器、带版本的小型 C ABI、Runtime 构建目标、完整版本清单与最小版本持有协议。
最小协议固定版本路径并保护持有者；本阶段不实现自动 GC，不覆盖或删除活动版本。P2/P3 以此作为前置能力。
接口提供 ABI 版本、结构大小、能力位、明确错误码及生命周期回调。
不把 Swift/ObjC 内部对象布局、私有 C 结构或全局符号作为长期 ABI 合同。
必须说明参数所有权、线程约束、回调寿命及错误传播方式。

`RuntimeContext` 至少显式传递：

- 应用身份、进程实例身份与授权信息；进程身份不能只用可复用的 PID。
- `runtimeRoot`：本次固定且不可变的完整运行库版本目录。
- `packageRoot`：本次固定的 APK、split APK、原生库与资产版本目录。
- `dataRoot`、`cacheRoot`、`configRoot`：该 App 的独立可写目录。
- 宿主窗口、输入、音频、通知、文件选择和应用生命周期回调。
- 已批准的资源预算、手动 JIT 值、版本使用凭据与功能支持范围。

消除运行时对 Husk 主程序容器、固定 bundle ID 和管理界面 singleton 的依赖。
可保留只在单个进程内有效的运行状态；不为了共享库而共享可写 Java 堆。
首个核心模块的构造函数不得提前执行 Guest 初始化或进行大型内存分配。
iOS 受保护模式的重资源装载必须等待 P3 的配额与准入完成；JIT helper 同样受此约束。Mac 受控功能原型按第 2 节单列能力与有限工作集，不把模拟控制当作这一条件已通过。
完整包包括库、dex/jars、字体、证书、ANGLE/图形依赖、资源及兼容声明。
对全部依赖检查解析路径，禁止一部分指向新版本、一部分指向旧版本。
按依赖清单确定实际打包范围，不能直接复制原 Husk 所有后端作为默认 Runtime。

**验收**：同一启动器加载两个兼容版本；缺库、ABI 不符时在 Guest 执行前退出初始化。
宿主测试验证路径与所有权；目标设备验证动态装载、签名和 UI 主线程要求。
**停止条件**：必须依赖管理器内存对象、隐式 `Bundle.main` 资源或未版本化符号才可启动。

## 5. P2：独立安装、身份与沙箱

**前置条件**：Mac 部分对应 M2，依赖 M1；iOS 部分需 P1 协议/包格式稳定并通过 P0 注册与权限探针。

产物：应用注册表、安装事务、包版本目录、沙箱规则、进程身份映射和受控 IPC。

安装流程按“解析 → 验证 → 暂存 → 注册 → 提交”设计，每一步可中断恢复。
APK 解析与资源处理放在低权限辅助进程；特权安装服务只接受经过验证的操作。
包名、图标路径和 manifest 内容均视为输入，不用于直接拼接特权文件路径。
每 App 使用稳定 bundle ID，更新时保留身份和私有数据；不同 App 的容器不混用。
普通用户数据、可丢弃缓存、只读安装内容和共享文件授权分别定义生命周期。
文件共享使用显式授权；不得给全部 App 一个任意可写的全局目录。
公共 Runtime 和版本索引只允许发布服务写入，APK 进程仅获得需要的只读权限。

为 guest PID/UID、组件进程名与宿主 PID/启动代次建立明确映射。
拒绝 guest 对无归属进程发信号、调试、读写内存；审计所有透传宿主 API 的入口。
拒绝过期身份凭据；防止 PID 重用使旧请求命中新启动的其他 App。
跨 App 的组件调用必须通过身份认证、组件导出声明与授权判断。
共享服务对每 App 的请求大小、队列、并发、超时和返回数据设置独立额度。
服务端不信任调用者自报的包名或 PID；业务错误返回调用方，不能终止服务本身。
共享系统服务只取消归属该 App 的会话，不得因 A 超限终止 B 也使用的系统服务。

卸载先停止本 App 新启动，结束或等待相关进程，再注销并回收本 App 的版本引用。
需要等待活动引用时可先标记待删除，不能删除其他 App 正在使用的公共版本。
更新 APK 不覆盖活动 `packageRoot`；新进程采用新包，旧进程保留旧包资源。
同一安装身份的更新切换遵循 P4 的执行代次规则；不允许新旧代次同时写同一个数据目录。
同包名 APK 更新需验证签名者连续性或受支持的签名轮换，不匹配时不能覆盖并取得原数据。

**验收**：A/B 独立注册；A 越权信号、文件写入、IPC 冒用被拒绝；事务中断后可恢复。
**停止条件**：依赖 root Guest、宽泛沙箱豁免或可写公共代码才能工作。

## 6. P3：资源预算与执行前准入

**前置条件**：Mac 策略与故障注入对应 M3，真实硬限制能力单列；iOS 部分需 P0 验证限额、P2 建立可信 App 归属与进程身份。

产物：预算策略、启动准入协议、每进程系统硬限制适配、辅助资源账本和故障行为。

预算至少包括：宿主基础开销、Java/原生堆、线程栈实际占用、JIT、图形和媒体资源。
分别记录虚拟地址保留与计入系统限额的内存；不能把两者直接相加当物理内存。
同一物理代码页的共享与计费按当前宿主实测处理，iOS 结果由 P0 确认；容量规划不得依赖未经证明的去重收益。
保留系统余量、运行中 App 预算、并发启动峰值和有限的退出清理余量。
总预算配置是运行策略，不表示内核已替这些 App 永久预留物理页。

每 App 边界必须记录：

- 主进程及所有由它请求创建的工作、渲染、WebKit、JIT 和媒体辅助进程。
- 各进程 active/inactive 限额、配额生效证据和合计约束。
- 可归属共享服务资源的上限；无法归属的部分明确计入系统余量或拒绝支持。
- 辅助进程新增、退出、被系统重建时，身份、预算和限制的更新规则。
- 前后台切换是否改变系统额度；改变前先判断现有占用能否满足新状态。

启动准入顺序必须是：

1. 核对所属执行代次、固定兼容 Runtime 与 APK 版本，取得与 GC 互斥的使用凭据。
2. 启动器按固定版本申请 App 预算与启动峰值，服务原子预留，避免同时启动超售。
3. 新进程获得并核验有效系统硬限制；辅助进程同样先完成配额建立。
4. 加载并校验运行库，按用户设置申请 JIT，加载重资源并启动 Guest。
5. 启动完成后先释放临时资源，确认全部所属进程占用和有效系统限额收敛至稳态份额，再协调归还启动峰值额度；不能只凭首帧或初始化回调归还。
6. 失败时先停止本次工作并确认线程、异步消费者、所属辅助进程和相关资源退出/释放，再回收本次额度与版本持有。不能证明清理完成时结束本 App 的相关进程并等待系统确认；错误界面若继续存活，基线开销仍计入预算。不确定时保留记录，不得关闭 B 来腾预算。

轻量启动器自身仍需内存；P0 必须测量限制生效前的最小开销，并纳入启动余量。
任何 Guest 原生构造函数、JIT 分配或辅助进程大型资源申请都不得早于硬限制生效。
用户设置的手动 JIT 不适合当前预算时，提示调整或等待；不自动缩小 JIT 或线程栈。
Java 堆限制、allocator 包装和压力回调作为提前回收手段，不能代替系统硬限制。
低频遥测用于诊断和策略，不得用“每隔若干毫秒查看后杀进程”证明隔离保证。
发生归属本 App 的超额时，限制或终止本 App；记录超额原因及 B 的持续运行证据。
系统仍可能因外部压力回收进程；该事件单独归类，不伪装为已实现绝对隔离。

**验收**：并发启动不会超售；A 的堆、线程、JIT、GPU/辅助资源压力分别得到约束。
**停止条件**：只能靠轮询、只限制 Java 堆、辅助进程无限制，或需关闭系统内存保护。
遇到上述情况只保留普通进程隔离能力说明，不能交付强内存隔离声明。

## 7. P4：版本发布、使用凭据与回收

**前置条件**：Mac 部分对应 M4，依赖 M1–M3 的包/身份/准入协议；iOS 部分依赖 P1/P2，受保护并发验证还依赖 P3。

产物：不可变版本仓库、原子索引、按 App 固定版本策略、使用凭据和恢复日志。

发布先写独立暂存目录，验证完整性、签名、ABI 和全部依赖，再提交版本索引。
选版本与登记使用必须与删除互斥，不能在读取索引和登记之间被 GC 删除。
新进程解析一次版本路径；之后全部依赖和延迟打开资源使用固定目录。
运行中升级不替换既有进程的代码；后台恢复也不切换其运行库。
保留默认版本与可选择的兼容版本，不因全局更新强迫每个 App 同时升级。

使用凭据绑定 App 身份、进程实例、Runtime 版本和 APK 版本。
进程退出回调只作为优化；SIGKILL、Jetsam、崩溃和断电都可能没有回调。
服务根据操作系统进程身份与启动代次确认存活，避免 PID 重用或过期记录误判。
管理服务重启后重新核对凭据；无法确认时先保留文件，不能猜测“已无进程”。
设备重启后区分旧启动周期与新进程；保留人工固定和回退策略所需版本。
GC 同时检查活动进程、安装/更新事务、固定版本和回退保留，不仅检查当前默认值。
管理服务暂时不可用时，已运行 App 应继续；新启动可明确失败，不能绕过配额准入。
服务失联时保留已有系统限额，冻结新准入、扩额及 GC；不能以 TTL、心跳缺失或后台挂起释放额度。恢复后先重建可信账本，再开放准入，禁止清零账本或统一结束现有 App。
持有协议须由每个实际使用版本的进程执行，GC/安装器/卸载器遵守相同共享与排他协议，锁对象不可被替换。普通打开目录句柄不能单独防止 unlink；具体原语必须经过挂起、强杀与服务重启测试。

同一安装身份以执行代次绑定 Runtime、APK、配置快照与数据格式代次；主进程和仍存活的辅助进程保持一致。主进程退出后重开，首期先收拢旧代次全部进程，再选新版；后续若支持同代次恢复，须明确复用旧版并单独验收。Runtime-only 更新也不能让新主进程与旧辅助进程混写数据。

APK、split 和资产使用不可变包版本；AOT/派生缓存至少按 App、APK、Runtime ABI、架构隔离。
涉及签名或代码转换的缓存还要包含对应签名/转换版本，防止错误复用。
缓存可重建；用户数据不得与 Runtime GC 一起删除。
运行库回退不等于用户数据格式回退；有数据迁移时另行设计备份和兼容恢复。

**验收**：边运行边升级、发布中断、服务崩溃、进程强杀、重启和并发 GC 均不产生混版。
**停止条件**：覆盖活动版本文件、靠进程主动释放保证 GC，或回退会破坏用户数据。

## 8. P5：原生体验与 Android 服务语义

**前置条件**：Mac 部分对应 M5，明确资源能力边界；iOS 部分需 P2 身份与 P3/P4 资源、版本边界通过。

产物：按 App 归属的系统集成、生命周期映射、支持能力表和分层兼容样本。

首批实现桌面启动、App 切换器、旋转、安全区、键盘、文件选择与分享。
接入按 App 独立授权的通知、通知点击路由、音频会话及被系统终止后的状态恢复。
URL scheme、权限描述、分享扩展和其他需静态声明的能力纳入外壳版本管理。
启动器接口或权限声明变化时进行就地外壳更新，不承诺运行库升级覆盖全部变化。
后台任务按实际能力映射 Service/Job/音频等语义；锁屏执行与 UI 绘制分开处理。
用户完全关闭时记录带执行代次的停止状态、取消重启请求并收拢辅助进程，拒绝旧代次延迟请求，不能被 START_STICKY 自动拉起；无法可靠识别用户强退时不启用自动复活。验证锁屏数据保护和管理服务死亡时后台断言的实际行为。
Android 远程推送与 iOS APNs 不视为自动互通；各提供方能力单独核查和测试。

后续再实现 APK 内 `android:process`、跨进程 Binder、Provider、死亡通知和恢复。
新增 Android 子进程仍属于同一 App 的资源边界，不获得无限新增预算。
跨 App 组件失败必须返回可处理错误；不让依赖方通过同步无限等待阻塞 UI。
暂不支持的组件或权限明确报告，避免用固定成功返回值造成“看似正常”的状态。

**验收**：通知、分享、权限与后台事件始终归属正确 App；拒绝授权和进程重建可恢复。
**停止条件**：关键系统行为只能由管理器冒名执行，或后台依赖无法限制的常驻共享 Guest。

## 9. P6：验收矩阵与故障注入

**前置条件**：按宿主分别验收，各阶段产物可测试；Mac 证据只关闭 Mac 项，iOS 目标设备保留诊断与恢复路径。
产物：能力报告、回归矩阵、故障注入结果及明确支持范围；未测项保持未测。

| 类别 | 故障或场景 | 应观察的结果 |
| --- | --- | --- |
| 崩溃 | A 原生异常、Java 致命错误、主动退出 | B 继续，A 资源与引用最终释放 |
| 内存 | A 触页增长、线程增长、JIT、纹理/视频和辅助进程压力 | 对应额度生效，超额处理定位 A，记录 B 状态 |
| 并发 | A/B 同时冷启动、反复创建辅助进程 | 预算不超售，拒绝结果清晰，无隐式缩配额 |
| 额度退回 | 初始化后仍占用峰值、限额尚未降低、部分启动失败 | 未收敛前保留峰值额度；确认消费者与资源释放后才回收 |
| 身份 | A 对 B 发信号、访问容器、伪造包名、复用旧 PID 凭据 | OS/服务权限拒绝，B 数据与生命周期正常 |
| 共享服务 | IPC 洪泛、超大消息、服务崩溃和重启；服务死亡后 A 再越限 | 既有限额仍生效；新增准入/扩额被冻结；B 不被主动结束 |
| 升级 | 活动旧版、新版发布一半、错误签名、ABI 不符 | 固定完整版本；失败发布不切换默认值 |
| 回收 | 强杀持有者、重启服务、GC 与启动竞争、设备重启 | 无活动版本误删，无 PID 重用误判 |
| APK 更新 | 旧包仍运行时更新、卸载/更新事务中断 | 数据与活动资源保持一致，可恢复事务 |
| 执行代次 | 仅升级 Runtime 后主进程崩溃，旧辅助进程仍存活 | 收拢旧代次后再启动新版，避免跨 Runtime 混写数据 |
| 系统集成 | 拒绝权限、通知冷启动、分享、音频中断、锁屏 | 归属正确 App，行为符合已声明能力 |
| 用户强退 | 主进程被用户关闭，辅助进程存活且已有重启/定时请求排队 | 收拢所属代次、取消旧请求；直到用户显式打开才再启动 |
| 外部压力 | 原生第三方 App 消耗内存、温度与系统调度变化 | 记录系统限制，不把一次存活解读为绝对保证 |

已有可复用宿主回归入口：`tests/translation-layer/run_session.sh`、`run_session_io.sh`、
`run_reopen_boot.sh`、`run_web_session.sh`、`run_compressed_heap.sh`、`run_string_oom.sh`，
以及 `tests/java-framework/run.py`；它们不能替代独立 iOS App 和系统限额测试。
2026-11-06 已在 Mac 执行其中 `run_session_io.sh` 和 `run_reopen_boot.sh`，结果见第 11 节。其余入口未在本次运行；具体环境要求以各脚本和 README 为准。
